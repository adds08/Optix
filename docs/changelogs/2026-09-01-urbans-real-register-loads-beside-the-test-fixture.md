# Urban's real register loads beside the test fixture, not instead of it

Urban's own data arrived as two files — an enclosed-trailer workbook with a sheet per
trailer, and a PDF of the company vehicle list — with the register due to go live the
same afternoon. Neither file is clean: names are hand-typed and sometimes spelled two
ways, job cells hold several numbers or a department name, one truck is marked "remove
it from portal", and two trucks share a licence plate. The task was to get that data
loadable without inventing any of the missing pieces, and it turned into a second,
larger finding about what the seed actually is.

## What changed

### The source files are parsed into templates, and nothing is guessed

`docs/data/build_import.py` reads the `TE` summary sheet and every `TE-*` trailer sheet,
and carries the truck list transcribed verbatim — misspellings included, because
correcting a name invents a person. It emits `docs/data/import/*.csv` for the rows that
can be trusted and `rejects.{json,csv}` for the rows that cannot, each with the reason
and a severity.

The reject rules are not stylistic. The target schema has real constraints, and a load
that guesses a missing value produces either a collision or a wrong custodian:

- `vehicle_one_truck_per_foreman_uq` (migration `0030`) is a unique index on
  `(tenant_id, foreman_employee_id)` for company-owned trucks. Two people in the source
  hold two trucks each, which does not warn — it aborts the load. The first truck keeps
  the custodian; the later one loads with none and is reported.
- A duplicate licence plate, a sixteen-character VIN and a plate reading `Temproary` are
  each recorded rather than normalised into something plausible.
- Job cells holding `25011/25012`, `25001 & 25002`, `Safety Department` or the
  Excel-mangled `2,201,826,002` yield no project link. The vehicle still loads.

`build_report.py` renders the same JSON as `docs/data/import/data-issues.html`, grouped
by who can fix each item rather than by severity, because the audience is the Urban
team correcting spreadsheets.

### Identity collisions are decided by a human and recorded in the source

Seven pairs of names could each be one person or two. They are resolved in a `DECISIONS`
block at the top of `build_import.py`, with the evidence, because the alternative is a
merge rule nobody can audit later.

`JUAN MARTINEZ` (TE-028, NEX #22017) and `Juan Martinez (1975)` (TRK-044, job 22017) are
one man; `Juan Carlos Martinez` (TRK-032, job 25001) is a second. The `(1975)` is the
evidence — somebody at Urban added a birth year precisely because two Juan Martinezes
exist.

The other five near-matches are kept **separate** on Urban's instruction, which reverses
an earlier pass at this data (`generate_seed.py`'s `NAME_TOKEN_ALIASES` merged two of
them). The reasoning is worth keeping: a wrong merge hands one man another man's tools,
while a wrong split leaves two obvious duplicates a human can merge from the register in
seconds. Take the reversible error.

### The Equipment Yard stops being two projects

Job `24002` was doing two contradictory jobs in the source: the yard on `TE-007`, and a
real job carrying a superintendent (TRK-036), a surveyor (TRK-038), a traffic control
foreman (TRK-020) and a field engineer (TRK-045). A yard does not have a surveyor.

So the yard carries no job number and `24002` becomes its own project. Its proper name is
in neither file, so it loads as `Job 24002` and is flagged for renaming rather than
guessed. The name `Equipment Yard` is pinned, because `jobsites/page.tsx` matches the yard
by string (`YARD_PROJECT_NAME`) and renaming it would draw the yard as an ordinary job
card — the exact bug that page exists to prevent.

### Two datasets, selected at runtime

Urban's register lives in `packages/db/src/seed-data.urban.ts`, generated by
`build_seed_data.py`. `seed.ts` picks between it and the existing fixture on
`SEED_DATASET`, using namespace imports destructured into the same names so no downstream
line changed. The static vocabularies stay shared — a category and a unit of measure mean
the same thing whichever register is loaded — and the seed now logs which one it wrote.

Passwords split the same way. The fixture keeps `stinventory-demo` because `e2e/roles.ts`
signs every browser test in with it and the login page offers one-click accounts that use
it. The urban dataset seeds one owner, `optix_it@optixtec.com`, taking
`SEED_OWNER_PASSWORD` or a random password printed once, so no credential for a real
deployment is ever in git.

## What was found while building it

**The seed was serving two incompatible purposes, and only one of them was written down.**
Replacing `seed-data.ts` with Urban's data typechecked, ran, and produced a correct-looking
register — then turned CI red. Five of `rbac-matrix.test.ts`'s thirty-six tests stopped
being *runnable*, every one reporting `seeded account missing`. That test proves the
visibility ladder narrows by asserting a PM and a superintendent see deliberately
different sets of tools, which only holds for people engineered to differ; Urban's staff
are whoever the spreadsheets say. A security test that cannot run is worse than one that
fails, because nothing measures the permission system while it is gone. The fixture is a
fixture, and that is now stated in `seed.ts` rather than implied by the data.

**Three demo fixtures inside `seed.ts` were silently load-bearing**, and all three were
found by running the seed against real data rather than by reading it:

- The personal-allowance truck lookup was `vehicleRows[vehSpecs.findIndex(...)]!.id`. A
  fleet that is entirely company-owned makes `findIndex` return `-1`, `vehicleRows[-1]`
  undefined, and the whole seed dies on `.id`.
- The desk approval queue hardcodes demo tools, foremen, projects and trailers
  (`TOOL-0053`, `e-fm005`, `p-nex-22017`, `l-TE-011`). Absent them it inserted a custody
  row with a null custodian and hit the NOT NULL constraint.
- `admin@stinventory.local` was named in three places — the asset writer's `createdBy`,
  the genesis ledger actor and the desk message author — each asserting non-null. Deleting
  one account broke the seed in three places at once. They now resolve through a single
  `seedActor`.

**One foreman really does run two loaded trailers.** FELIPE PORTILLO holding both TE-017
and TE-027 was raised as an anomaly and ruled on as one — wrongly. `schema/location.ts`
already records it: the truck uniqueness index is trucks-only *because* a trailer version
"would fail the migration on correct production data", naming these two trailers. The
generator's `NO_CUSTODIAN_TRAILERS` currently holds `TE-027` on that mistaken basis, which
leaves its thirty tools with no custodian. Emptying that set restores him.

**`generate_app_seed.py` is stale in shape, not just in data.** It emits a `costCenter`
field `ProjectSeed` no longer has, and omits `categorySpecs`, `roleSpecs`, `uomSpecs` and
`companyRoleSpecs` entirely — running it would have deleted four exports `seed.ts`
imports. It was not used; `build_seed_data.py` replaces only the data blocks.

## Verified

Run against the local stack in the api container, so the database-backed suites really
ran:

- `pnpm turbo run test` green across every package, and `rbac-matrix.test.ts` back to
  36 of 36 after the split.
- `pnpm typecheck` clean across the workspace; `pnpm lint` clean.
- Both seed paths run end to end from `SEED_RESET=1`. The fixture path seeds its usual
  users and assets; `SEED_DATASET=urban` seeds Urban's projects, employees, vehicles and
  tools with every ledger row carrying a complete `toState` — confirmed by
  `select count(*) from tbl_ops_transaction where to_state is null`, which returns zero,
  so the fold rebuilds rather than blanking custody.
- `select count(*) from tbl_entity_project where name ilike '%equipment yard%'` returns
  one.
- `git diff 4ffd255~1 HEAD -- packages/db/src/seed-data.ts` is empty, which is the check
  that the fixture was restored byte-for-byte rather than approximately.

**Not verified:** no browser was opened, so how Urban's register renders — the jobsites
board with real crews, the equipment page with forty-nine trucks — is untested. The e2e
suite was not run. Neither the dev droplet nor production has been loaded; only local.

## Deliberately not done

- **The equipment-type taxonomy was not added.** Urban asked for vehicle / attachment /
  heavy equipment / other. `vehicle.equipmentClass` exists (`vehicle | heavy`) but is
  never written by any UI, and there is no `attachment` value. The templates emit an
  `equipment_kind` column for it; the register still loads trailers as
  `vehicleType: 'trailer'`. Adding the field is schema, migration, router and form work.
- **Rows with missing information were not filled in.** That was the explicit instruction
  and it is the reason the rejects file exists.
- **The `NODE_ENV=production` guard was not removed**, only re-explained. Its reason
  widened rather than disappeared: `SEED_RESET=1` deletes every tenant, employee, vehicle,
  asset and ledger row, dropping the ledger's append-only trigger to do it.

committed mid-task from outside the session with `#` as the subject. The seed work is

unbroke CI), merged to `main` as `d032107`.

Committed and pushed on both branches. **Not loaded anywhere but a local database** — the
deploy ships code, and Urban's rows reach an environment only when
`SEED_DATASET=urban SEED_RESET=1 pnpm seed` is run on that box, which wipes before it
writes.
